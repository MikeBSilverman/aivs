# Deploying AIVS

Operator guide for the AIVS sharing server: two hosting modes, the certificate
authority, member enrolment, network placement, and the exact first-run
sequence.

Everything here assumes a single Linux host with Docker Engine 24+ and the
Compose v2 plugin. Nothing in this directory needs Kubernetes, and nothing in
it needs a CA daemon.

---

## 1. The security model in one page

AIVS authenticates member organisations with mutual TLS. The proxy terminates
that TLS and tells the application who the caller is using HTTP headers — which
would be forgeable, so three controls stack to make it safe:

| # | Control | Where it lives |
|---|---------|----------------|
| 1 | The application publishes **no host port**. It is reachable only from the proxy, over a compose-internal network. | `docker-compose.yml` — the `app` service has no `ports:` key |
| 2 | The proxy **unconditionally overwrites** every identity header on every request, so a client-supplied value never survives. | `deploy/nginx/snippets/aivs-identity-headers.conf` |
| 3 | The proxy **proves it is the proxy** with a shared secret in `X-Proxy-Auth`, compared in constant time, and connects from a pinned `/32`. | `AIVS_PROXY_SHARED_SECRET`, `AIVS_TRUSTED_PROXY_CIDRS` |

A fourth property matters as much as the three above: **the application does not
trust the proxy's opinion of the certificate.** nginx forwards the full escaped
PEM in `X-Client-Cert`, and the application re-parses it, computes the SHA-256
fingerprint itself, and re-checks the validity window. nginx's own
`$ssl_client_fingerprint` is SHA-1 and is used only for rate-limit bucketing —
never for identity.

**The identity of a member is the SHA-256 fingerprint of its certificate**,
registered against an organisation in the AIVS database. Not the DN, not the
serial, not the CN. `issue-client.sh` prints it; nothing works until it is
registered.

## 2. Hosting modes

### Mode A — ISAC self-hosted

The ISAC runs the stack on its own infrastructure and operates its own CA. The
ISAC is the trust anchor for its members: it decides who is enrolled, it holds
the issuing key, and it is the only party that can mint a member identity.

- Root CA generated by `deploy/ca/init-ca.sh`, then **taken offline** to
  removable media under dual control.
- Issuing CA key stays on the host at mode 0600 and signs member certificates.
- Aequora ships code; it holds no key material and has no access path.
- Network placement is the ISAC's choice — see §5.

Choose this when the ISAC's own risk policy will not accept a third party
holding the ability to issue member identities. That is the common answer for a
financial-sector ISAC, and it is the mode the defaults in this repository
assume.

### Mode B — Aequora-managed

Aequora operates the stack for the ISAC. Same code, same compose file, same CA
scripts; what differs is who holds the keys and who is on the pager.

- Aequora holds the issuing CA key and runs enrolment on the ISAC's written
  instruction.
- The root key is generated in a ceremony with the ISAC present and split
  between ISAC-held and Aequora-held offline media, so that neither party can
  unilaterally issue a new intermediate.
- The WireGuard overlay (§5) is the default here, and AIVS is not exposed to
  the public internet at all.
- The ISAC retains the authoritative membership list; Aequora's CA operations
  reconcile against it at each access review.

The material difference for a third-party risk review is the CA: in Mode B,
Aequora can issue a certificate that AIVS would authenticate. It cannot,
however, authorise one — registering a fingerprint against an organisation is a
database operation the ISAC's own operators perform and the append-only audit
log records.

## 3. First run — the exact order

The order is not arbitrary. The CA must exist before the proxy starts, because
the proxy's trust anchor and server certificate are mounted from
`deploy/ca/out`; the volume mount fails if that directory does not exist.

```bash
# 0. Prerequisites: Docker Engine 24+, the Compose v2 plugin, openssl 1.1.1+,
#    bash 4.3+. Check with:
docker compose version && openssl version && bash --version | head -1

# 1. Configuration. Every secret is generated here, none is defaulted.
cp deploy/env.example deploy/.env
chmod 0600 deploy/.env
$EDITOR deploy/.env
#    - AIVS_PROXY_SHARED_SECRET   openssl rand -base64 48
#    - AIVS_SESSION_SECRET        openssl rand -base64 48
#    - AIVS_DB_PASSWORD           openssl rand -base64 36 | tr '+/' '-_'   (URL-safe!)
#    - AIVS_CA_DIR                ABSOLUTE path to deploy/ca/out
#    - AIVS_PUBLIC_BASE_URL       exactly what members will dial, https://
#    - AIVS_BIND_PORT             only if 443 is taken; then the base URL carries it

# 2. Create the certificate authority. Prompts twice for the root passphrase.
deploy/ca/init-ca.sh --org "Example Financial ISAC" --country US

# 3. TAKE THE ROOT KEY OFFLINE. init-ca.sh prints the procedure; do it now,
#    not "after go-live". Until it is done this is a single-tier CA.

# 4. Issue the proxy's server certificate. --hostname must be the name members
#    will actually connect to.
deploy/ca/server-cert.sh --hostname aivs.example-isac.org
#    On an overlay deployment, add the overlay address as a SAN:
#      deploy/ca/server-cert.sh --hostname aivs.example-isac.org --san-ip 10.88.0.1

# 5. Let the container read the server key (nginx runs as uid/gid 101).
#    Owner rather than group: a bind mount shares the host's numeric id space,
#    so gid 101 on the host is whatever that host already assigns it.
sudo chown 101:101 deploy/ca/out/nginx/server.key
sudo chmod 0400 deploy/ca/out/nginx/server.key

# 6. Network allowlist. The shipped default permits private and overlay ranges
#    only; a publicly reachable deployment must replace it. See §5.
cp deploy/nginx/allowlist.conf.example deploy/nginx/allowlist.conf
$EDITOR deploy/nginx/allowlist.conf
#    then point the proxy's mount at it in docker-compose.yml:
#      ./deploy/nginx/allowlist.conf:/etc/nginx/allowlist.conf:ro

# 7. Build and start the database only, then apply migrations. Running
#    migrations before the app serves traffic avoids a window where handlers
#    query a schema that does not exist yet.
docker compose --env-file deploy/.env build app
docker compose --env-file deploy/.env up -d db
docker compose --env-file deploy/.env run --rm app alembic upgrade head

# 8. Start the whole stack.
docker compose --env-file deploy/.env up -d

# 9. Verify. All three services must report healthy.
docker compose --env-file deploy/.env ps
```

`scripts/e2e.sh up` runs this whole sequence against a throwaway CA and work
directory, then tests the result through nginx; `scripts/e2e.sh down` removes
it. It is the check for any change to the compose files or to `deploy/`:
`docker compose config` validates syntax, but the first defect it found -- the
app taking the proxy's static address, so the proxy could not start on any
clean host -- only appears when the stack actually starts.

`--env-file deploy/.env` is required on **every** compose invocation. Compose
looks for a `.env` beside `docker-compose.yml` by default, which does not exist
here; without the flag, compose aborts naming the first variable it wanted. Set
it once per shell if you prefer:

```bash
export COMPOSE_ENV_FILES=deploy/.env   # Compose v2.24+
```

### Smoke test

From a host that is permitted by the allowlist, using a member certificate:

```bash
curl -sv --cert  deploy/ca/out/clients/example-bank/example-bank.crt \
        --key   deploy/ca/out/clients/example-bank/example-bank.key \
        --cacert deploy/ca/out/ca-chain.pem \
        https://aivs.example-isac.org/taxii2/
```

Then confirm the proxy's JSON access log shows the real source address, not a
Docker bridge gateway — if it shows a gateway, the IP allowlist is inert (see
the Docker caveat in `deploy/nginx/allowlist.conf.example`):

```bash
docker compose --env-file deploy/.env logs proxy | tail -1
```

And confirm that a request **without** a certificate is refused at the
handshake:

```bash
curl -sv --cacert deploy/ca/out/ca-chain.pem https://aivs.example-isac.org/taxii2/
# expected: TLS alert, or HTTP 403 client_certificate_required
```

## 4. The CA, end to end

Everything lives in `deploy/ca/`. There is no CA daemon — `openssl(1)` driven
by four scripts, so the issuing key is loaded only for the seconds it takes to
sign and there is no additional network service in the review scope.

```
deploy/ca/
  openssl.cnf         policies and extensions; the single source of truth
  _lib.sh             shared validation helpers (sourced, not executed)
  init-ca.sh          create root + issuing CA                    [once]
  server-cert.sh      issue the proxy's server certificate        [~yearly]
  issue-client.sh     issue a member certificate                  [per member]
  revoke.sh           revoke, and regenerate the CRLs             [as needed]

  private/            0700  issuing key, root key (until moved offline)
  index.txt, serial   the issuing CA's database
  out/                public material — this is AIVS_CA_DIR
    ca-chain.pem      intermediate + root: the member trust anchor
    nginx/            server.crt, server.key
    crl/              root, intermediate, and the concatenated crl-chain.pem
    clients/<slug>/   per-member certificate, CSR, fingerprint
```

**Two tiers, and why.** The issuing key must be usable unattended on a host
that also runs a public-facing service; assume it can be stolen. With a
single-tier CA, recovering from that means distributing a new trust anchor to
every member out of band. With an offline root, recovery is: revoke the
intermediate, sign a new one from the root, re-issue member certificates —
members' trust anchors never change.

**Key algorithm.** ECDSA P-384 by default: CNSA-1.0 / NIST SP 800-131A
acceptable well past 2030 at a ~192-bit security level, an order of magnitude
cheaper per handshake than RSA-4096, and supported by everything in scope.
`--key-alg rsa` gives RSA-4096 for members whose HSM cannot hold an EC key; the
two mix freely.

**Extension smuggling is not possible.** `openssl.cnf` sets
`copy_extensions = none`, so extensions come from the config and nowhere else.
A member CSR asking for `basicConstraints=CA:TRUE` and `serverAuth` yields a
certificate with `CA:FALSE` and `clientAuth` — verify it yourself with
`openssl x509 -text` after signing one.

### Enrolling an organisation

The preferred flow keeps the member's private key with the member.

```bash
# 1. The member generates a key and CSR and sends you ONLY the .csr:
#      openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-384 \
#        -keyout example-bank.key -out example-bank.csr -nodes \
#        -subj "/C=US/O=Example Bank NA/OU=example-bank/CN=Example Bank NA AIVS Client"

# 2. Issue. The script verifies the CSR's self-signature (proving they hold the
#    key), rejects weak keys, and refuses to overwrite an existing certificate.
deploy/ca/issue-client.sh --org-slug example-bank --csr /tmp/example-bank.csr

# 3. Register the printed SHA-256 fingerprint against organisation
#    'example-bank' in the AIVS portal. NOTHING WORKS UNTIL THIS IS DONE:
#    a validly issued certificate whose fingerprint is unknown is refused.

# 4. Send the member:
#      deploy/ca/out/clients/example-bank/example-bank.crt
#      deploy/ca/out/clients/example-bank/ca-chain.pem
#    plus their WireGuard peer config if you are using the overlay (§5).
```

If the member genuinely cannot produce a CSR, `--org "Example Bank NA"`
generates the key here. Hand it over encrypted and out of band, then
`shred -u` your copy. A key that has been emailed must be re-issued.

The `--org-slug` must match the organisation slug registered in AIVS. It is
validated as a DNS label (lowercase letters, digits, internal dashes), which is
also what makes it safe as a directory name.

### Renewal

Member certificates are valid one year, the proxy certificate 397 days
(the CA/Browser Forum maximum — this CA could issue for longer, but matching
the public limit keeps the rotation habit alive). There is no automatic
renewal. Put both in the operational calendar.

Renewal is a fresh `issue-client.sh` run into a new directory, registering the
new fingerprint in AIVS, and revoking the old certificate once the member has
cut over. AIVS can hold two fingerprints for one organisation during the
overlap.

### Revocation

```bash
# 1. FIRST: disable the certificate/organisation in the AIVS portal.
#    This is what actually stops access — immediately, on the next request.
# 2. Then record it in the CRL:
deploy/ca/revoke.sh --org-slug example-bank --reason keyCompromise
# 3. If using the WireGuard overlay, remove their [Peer] block and wg syncconf.
```

**The CRL is belt and braces, not the control.** AIVS revocation is
authoritative in the database. The CRL matters for anything outside AIVS that
consumes these certificates, and it is the only way the root can disown a
compromised issuing CA.

nginx's `ssl_crl` is shipped **commented out**, for two reasons a reviewer
should weigh rather than assume:

- OpenSSL applies `CRL_CHECK_ALL` once `ssl_crl` is set, so the file must
  contain a current CRL for every CA in the chain. `revoke.sh` produces exactly
  that as `out/crl/crl-chain.pem`.
- A CRL past its `nextUpdate` makes nginx reject **all** handshakes. Enabling
  it converts a missed cron job into a total outage.

If you enable it, schedule regeneration well inside the CRL lifetime (30 days
for the issuing CA, 180 for the root) and reload the proxy afterwards:

```bash
deploy/ca/revoke.sh --gencrl-only
docker compose --env-file deploy/.env exec proxy nginx -s reload
```

Refreshing the root CRL requires the offline media: mount it at
`deploy/ca/private/root`, run `revoke.sh --gencrl-only --root-crl`, and remove
it again.

## 5. Network placement

Two options, both defence in depth on top of mutual TLS. Neither replaces it.

### WireGuard overlay — recommended

Every member peers into an overlay and AIVS publishes port 443 on the overlay
interface only. Nothing is exposed to the public internet: WireGuard does not
respond to unauthenticated traffic, so a port scan of the host finds an open
UDP port that says nothing back.

The two controls compose cleanly — **WireGuard authenticates the host, mTLS
authenticates the organisation** — and neither answers the other's question.
A member laptop can be a legitimate peer while presenting a certificate AIVS
has revoked; a valid certificate from an unknown host is what a stolen
certificate looks like.

Setup: `deploy/wireguard/wg0.conf.example` (hub) and
`member-peer.conf.example` (member). Then:

- `AIVS_BIND_ADDRESS=10.88.0.1` in `deploy/.env`
- `allow 10.88.0.0/24; deny all;` in `deploy/nginx/allowlist.conf`
- host firewall: UDP/51820 open, TCP/443 closed
- issue the server certificate with `--san-ip 10.88.0.1`

Removing a peer is instant and does not depend on a member's public address
staying put. It is not a substitute for revoking their certificate — do both.

### IP allowlist — when members must connect directly

`deploy/nginx/allowlist.conf`, one `allow` per member egress range with the
organisation slug in a comment so the list can be reconciled against the AIVS
organisation table at each access review. Expect churn: a stale entry causes a
member outage that presents as a TLS problem.

**Verify `$remote_addr` is real.** With Docker's default iptables DNAT the
source address is preserved, but connections arriving through the userland
proxy are rewritten to the bridge gateway — and then every client appears to
come from `172.x.0.1` and the allowlist silently permits everyone. The smoke
test in §3 checks this.

### Network topology inside the stack

Three networks, so reachability is a property of the topology rather than of
everyone remembering to configure a firewall:

- `frontend` — proxy ↔ the published port. Nothing else.
- `backend` (`172.29.10.0/24`) — proxy ↔ app. The proxy has the static address
  `172.29.10.2`, which is what `AIVS_TRUSTED_PROXY_CIDRS` pins to a `/32`. Not
  internal, because the app needs egress for outbound webhook delivery.
- `data` (`172.29.20.0/24`, `internal: true`) — app ↔ db. No route off the host
  in either direction, so a SQL-injection foothold has no egress to exfiltrate
  over.

If you change the `backend` subnet, change it in **three** places: the network
definition, `AIVS_TRUSTED_PROXY_CIDRS`, and the `allow` line on nginx.conf's
internal health listener. Nothing derives one from the others.

## 6. Operations

### Health

```bash
docker compose --env-file deploy/.env ps
```

- **app** — runs `python -m aivs_server.config`, which constructs `Settings`
  and therefore exercises every validator including
  `validate_production_posture`. A container running with a dev bypass enabled,
  or a malformed CIDR, reports unhealthy rather than quietly serving. It does
  not touch the database — that is the db service's own check.
- **proxy** — `GET /healthz` on an internal listener that requires no client
  certificate and is restricted to loopback and the backend subnet. It answers
  from nginx itself, so a slow database does not roll the proxy's health state
  and get a healthy proxy restarted during a database blip.
- **db** — `pg_isready` as the application's own role and database, so it fails
  if the role or database is missing, not merely if the postmaster is up.

### Logs

The proxy emits one JSON object per request on stdout, shaped for SIEM ingest:
request id, source address, TLS version and cipher, certificate subject DN,
issuer, serial, status, timings, and rate-limit outcome. `escape=json` in the
log format is load-bearing — without it a client-controlled field containing a
quote could forge log records.

The certificate fingerprint in that log is **SHA-1**, labelled
`client_fingerprint_sha1`. It is a connection-correlation aid. It is not the
identity, and correlating it against the SHA-256 values in AIVS will not work.

Logs are bounded at 20 MB × 5 files per service, so that a log flood — which
any unauthenticated party can trigger by opening connections — cannot fill the
disk and take the database down.

### Backup

- **Database** — `pgdata` named volume. `pg_dump` on a schedule; the audit log
  is append-only and enforced by a database trigger, so a restore that
  round-trips it is the only way to prove continuity.
- **CA** — `deploy/ca/private/intermediate.key` plus `index.txt`, `serial` and
  `newcerts/`. **The database files must be backed up with the key**, or you
  cannot revoke anything after a restore.
- **Root CA** — already on two encrypted offline volumes in separate locations,
  and you verified a restore before deleting the on-host copy. If you have not
  done that, do it now.
- **`deploy/.env`** — in the password vault, not in the filesystem backup.

### Upgrades

```bash
git pull
docker compose --env-file deploy/.env build app
docker compose --env-file deploy/.env run --rm app alembic upgrade head
docker compose --env-file deploy/.env up -d
```

For a deployment under third-party risk review, pin base images by digest — see
`AIVS_PROXY_IMAGE`, `AIVS_DB_IMAGE`, `AIVS_APP_IMAGE` in `deploy/env.example`
and the pinning note at the top of `packages/aivs-server/Dockerfile`. Record
the digests alongside the `uv.lock` hash in the release notes; a base image bump
is a change to review, not something to inherit implicitly on every rebuild.

### The development override

`docker-compose.dev.yml` publishes the application's port, mounts source over
the image, and enables `dev_trust_unauthenticated_proxy`,
`dev_expose_error_detail` and `dev_allow_private_webhook_targets`. **It removes
the identity boundary entirely.** Compose never applies it unless it is named
on the command line. If you find a host with it in `COMPOSE_FILE` or in a
systemd unit, treat that as an incident.

The application's own `validate_production_posture` is the backstop: it refuses
to construct a production `Settings` with any of those flags set, so the
override also has to declare `AIVS_ENVIRONMENT=dev` to work at all.

## 7. What a reviewer should check first

1. `docker compose --env-file deploy/.env config | grep -A2 'app:' | grep ports`
   returns nothing. The application must have no published port.
2. `deploy/ca/private/root/` does not exist on the host — the root key is
   offline.
3. `ls -l deploy/.env` shows `0600`, and `git status` shows it untracked.
4. `deploy/nginx/allowlist.conf` reflects the current membership list, and the
   proxy mount points at it rather than at the shipped `.example`.
5. The proxy's access log shows real source addresses, not a bridge gateway.
6. Every fingerprint registered in AIVS corresponds to a certificate in
   `deploy/ca/index.txt` with status `V`, and every `V` entry corresponds to a
   current member.
7. `openssl x509 -in <a member cert> -noout -text` shows `CA:FALSE`,
   `Digital Signature, Key Encipherment`, and `TLS Web Client Authentication`
   only.
